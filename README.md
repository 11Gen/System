# 中国名菜识别与营养摄入估算系统

基于迁移学习的菜品图像识别与膳食营养分析系统。上传一张菜品照片，自动识别菜名、估算热量与营养素摄入，并把多道菜汇总成一餐给出膳食提示。

**专业综合实训项目** · Python + PyTorch + Streamlit

---

## 这个项目做了什么

| 环节 | 内容                                                      |
| ---- | --------------------------------------------------------- |
| 识别 | 16 道中国名菜，MobileNetV2 迁移学习，两阶段训练           |
| 对比 | 同等条件下的传统方法基线（手写 HOG + KNN/SVM）            |
| 营养 | 每 100 g 营养值 + 份量模型，数据可逐条溯源                |
| 分析 | 一餐/全天汇总，对照《中国居民膳食指南》给供能比与用盐提示 |

支持的 16 道菜（含菜系）：

- **川菜**：麻婆豆腐、回锅肉、宫保鸡丁、鱼香肉丝、水煮鱼、酸菜鱼、夫妻肺片、口水鸡
- **粤菜**：咕咾肉、清蒸鲈鱼
- **苏菜**：小笼汤包、红烧狮子头
- **浙菜**：东坡肉、西湖醋鱼
- **闽菜**：佛跳墙
- **京菜**：北京烤鸭

### 两条识别路径

|            | 识菜                         | AI 识别                      |
| ---------- | ---------------------------- | ---------------------------- |
| 原理       | 本地 MobileNetV2 分类        | 调大模型视觉接口             |
| 能认多少菜 | 内置 16 道                   | 理论上不限                   |
| 速度       | 毫秒级                       | 几秒                         |
| 联网       | 不需要                       | 需要                         |
| 费用       | 0                            | 每次约 0.0005 元（DeepSeek） |
| 营养数据   | 配料配方来自地方标准，可溯源 | AI 估算配料，再查表计算      |

「AI 识别」是为闭集分类器的固有限制准备的补充手段：本地模型认不出的菜，
走这条路。它需要用户自己填一个 AI 服务的 API Key（只存内存，不落盘）。

> **如果 AI 认出的菜恰好在内置 16 道里**，系统会自动改用营养库里的权威数据，
> 不走 AI 估算 —— 因为那批数据来自地方标准，比 AI 估的准得多。

支持的 AI 服务：**DeepSeek**、**通义千问（阿里云百炼）**，以及任何
OpenAI 兼容的视觉模型服务（选「自定义」）。接口地址和模型名都可在界面上修改，
厂家更新模型名后用户自己改一下即可，不用等代码更新。

## 实测结果

> **所有数字均可现场复现。** 运行 `python tools/verify_repro.py` 会重新加载模型、
> 重新推理测试集，独立复算全部核心指标，并核对各实验产物之间的数字是否自洽。
> 当前结果：**17 项一致，0 项不一致**（详见交付文档里的「复现验证报告.md」）。

在 527 张同分布测试集上：

| 方法                      | Top-1 准确率 | 宏平均 F1  |
| ------------------------- | ------------ | ---------- |
| KNN (k=5)                 | 31.12%       | 0.3171     |
| 线性 SVM                  | 43.83%       | 0.4230     |
| RBF-SVM                   | 56.74%       | 0.5677     |
| **MobileNetV2（本方法）** | **94.88%**   | **0.9446** |

Top-3 准确率 99.43%。相比最优传统方法提升 **38.14 个百分点**。

### 消融实验

| 实验设置               | 测试准确率 | 相对完整方法 |
| ---------------------- | ---------- | ------------ |
| 完整方法               | 96.02%     | —            |
| 去掉数据增强           | 96.96%     | +0.94        |
| 只训练分类头（不微调） | 93.17%     | −2.85        |
| 不用 ImageNet 预训练   | 22.96%     | −73.06       |

两个结论值得注意：

- **预训练权重贡献了 73 个百分点**。有预训练时第一个 epoch 验证准确率就有 88.80%；
  随机初始化时第一阶段跑完 8 个 epoch 只有 20.30%，损失几乎不下降。
- **数据增强在本数据集上反而略降性能**（−0.94）。原因是该数据集图片均为
  600×600 专业拍摄、光照均匀，不存在增强所要模拟的尺度与光照变异。
  这个结论与常见做法不一致，但由实验数据支持——四个消融组的完整结果见
  `models/ablation_results.json`，或运行 `python tools/summarize_results.py` 看汇总。

### 跨数据集泛化与开集表现

在另一个数据源（`jiezh2/common-chinese-food`）上直接测试：

- 学过的类别（宫保鸡丁，140 张）：**97.14%**，与同分布测试集持平
- 未学过的类别（4 类共 596 张）：平均置信度 0.788（低于已知类的 0.945），
  但仍有 **85.9% 的样本置信度高于 0.5**

后者说明闭集分类器会对陌生输入给出自信的答案。为此项目实现了**拒识机制**：

用能量分 `logsumexp(logits)` 判断输入是否属于模型学过的范围，
阈值在 527 张已知图 + 596 张未知类图上标定为 **2.89**
（对应已知接受率 95%）。三种评分方法对比：

| 方法                     | AUROC      | 未知拒识率（已知接受率固定 95%） |
| ------------------------ | ---------- | -------------------------------- |
| MSP（最大 softmax 概率） | 0.8177     | 30.70%                           |
| 熵                       | 0.8240     | 38.26%                           |
| **能量（本项目采用）**   | **0.8489** | **47.82%**                       |

能量分显著优于直接用置信度，因为 softmax 的指数归一化会压平不同样本间
logits 的差异。这一机制已在界面生效：能量分低于阈值的输入会提示
「这看起来不是系统支持的菜品」，而不是输出一个可能错误的菜名。

> 局限：即使采用最优方法，5% 误拒率下也只能挡掉约一半陌生输入。
> 原因是评测用的未知类别（红烧肉、鱼香肉丝等）与训练集同属中式菜肴，
> 视觉上高度相似，这个开集任务比常用跨域基准困难得多。

### 营养估算方法验证

用第三方平台同时给出配方与官方营养值的菜品做回归检验，
平均绝对偏差 21.3%，最大 32.7%。偏差来源于配方差异与生熟重口径差异，
而非算法错误（若分母或单位有误，偏差会是数倍而非百分之几十）。

## 快速开始

### 1. 环境

需要 Python 3.10 以上。项目在 **Python 3.13.12** 上完成全部实验与验证，
在 **Python 3.14.3** 上也确认了依赖可正常安装。

```bash
pip install -r requirements.txt
```

CPU 就能跑完全流程。有 NVIDIA 显卡的话装上对应 CUDA 版 torch 会快不少
（见文末"训练耗时"）。

> **如果你用 PyCharm**：注意确认项目解释器选的是哪个环境。
> 一个常见问题是 PyCharm 自动建了 `.venv`，而依赖装在别处（比如 Anaconda），
> 于是报 `ModuleNotFoundError`。两种解决办法：
>
> - 在 `Settings → Project → Python Interpreter` 里切换到已装好依赖的解释器；
> - 或者就在当前解释器里执行上面的 `pip install -r requirements.txt`。

### 2. 获取数据

数据集通过 Kaggle 公开下载接口获取，**不需要注册 Kaggle 账号**：

```bash
python src/fetch_dataset.py --slug patzer0/16-famous-chinese-dishes --extract
```

约 500 MB，视网速 3~10 分钟。文件会解压到 `data/raw/16-famous-chinese-dishes/`。

> 如果这条通道在你的网络下不通，参考交付文档里的 `数据获取说明.md`（记录了几种备选方案及各自实测的可用性）。

### 3. 数据准备

```bash
# 清洗：按标注框筛选图片、裁剪、去重
python src/prepare_dataset.py --source dishes16

# 划分 train/val/test 并做图片完整性校验
python src/split_dataset.py
```

### 4. 生成营养数据库

```bash
python src/build_nutrition_db.py     # 按配料配方合成 16 道菜的营养值
python src/nutrition.py              # 自检：来源分布 + Atwater 自洽性
python src/check_nutrition.py        # 联网复核（需要网络）
```

### 5. 训练

```bash
# 传统方法基线（约 3 分钟，出对照组数据）
python src/extract_features.py
python src/train_baseline.py

# 深度学习主线
python src/train_cnn.py --epochs1 12 --epochs2 10 --tag main
```

### 6. 评估

```bash
python src/evaluate.py                       # 混淆矩阵、分类报告、错分分析
python src/evaluate.py --root data/dataset/cross_dataset/test --tag cross   # 跨数据集测试
```

### 7. 启动界面

```bash
streamlit run streamlit_app.py
```

浏览器打开 http://localhost:8501

### 重跑实验的完整顺序

想从零重跑一遍实验的话，顺序是：

```bash
python src/prepare_dataset.py --source dishes16   # 准备数据
```


## 几个实现上的说明

### 为什么选"菜肴 + 配料合成"而不是直接用现成的菜品营养值

中国食物成分表里**没有**"宫保鸡丁""东坡肉"这类菜肴条目——这不是推测，是对该库 259~1580 全部 1341 个条目做过逐条抓取核验后的结论。所以改用配料合成法：取各配料每 100 g 的官方值，按真实配方加权求和，再除以成品重量。配方、配料来源、计算方法全部记录在案，可以逐条验算。

这样做的另一个好处是：数据库里同时留下了配料表，界面上能直接展示"这道菜是由什么构成的"。

### 为什么营养数据要单独写一个复核脚本

取数过程中有一部分数据因为 USDA 官方 API 的免费额度限制（30 次/小时/IP）只能从镜像站取得。二手来源不能直接用，所以 `check_nutrition.py` 会重新抓取页面逐字段比对，并用 Atwater 系数（蛋白 4、脂肪 9、碳水 4 kcal/g）从三大营养素反算能量做自洽性检查。这个检查独立于数据来源，能发现抄录错误。

### 为什么训练要分两个阶段

换掉分类头后新头是随机初始化的，一开始梯度很大。如果直接全网络微调，这些梯度会顺着反向传播把预训练好的主干权重冲乱。先冻结主干让新头收敛，再用小一个数量级的学习率解冻后段微调，训练才稳定。

### 关于图片清洗

原始数据集是 YOLO 目标检测格式，很多照片里不止一道菜。直接当分类数据用会出现"一张图多个标签"的歧义。所以按标注文件筛选出画面里只有一道菜的图，并按框裁剪去掉多余的桌面和餐具。

## 已知局限

- **只认识这 16 道菜**。已实现拒识机制（`src/open_set.py`）来应对陌生输入，
  在 5% 误拒率下能挡掉约 47% 的未知菜品，但仍有相当比例会被错误接受。
  根本解决需要引入端到端开集训练方法。
- **份量靠估**：份量是营养估算最大的误差来源。同样一盘菜小碟和大盘能差一倍，所以界面上把份量做成了可调参数而不是写死。
- **营养数据仅供参考**，不能作为医疗或营养学建议。
- **部分营养数据来自镜像站**，因为 USDA 免费 API 额度限制。已逐条标注来源等级，可用正式 API key 升级为直连验证。
- **界面里的"膳食评分"是简化指标**，借用 Nutri-Score 的思路（有利因素加分、不利因素减分），并非欧盟官方算法。

## 环境问题排查

**`ModuleNotFoundError`（`torch` / `streamlit` 等）**
依赖没装到当前解释器，或者 PyCharm 选错了环境。先确认用的是哪个解释器：

```bash
python -c "import sys; print(sys.executable)"
```

再装依赖：`pip install -r requirements.txt`
另外确认 Python 版本 ≥3.10；PyTorch 的 wheel 按 Python 版本分别编译，
版本过新或过旧都可能找不到对应 wheel。

**`torchvision` 报 `operator torchvision::nms does not exist`**
torch 和 torchvision 版本不配套。两者必须按官方对应关系一起装，
不能各升各的。`requirements.txt` 里已给出配套下限，
出问题时用 `pip install --force-reinstall -r requirements.txt` 重装。

**图表里的中文变成方框**
系统缺少中文字体。代码里已按 `Microsoft YaHei → SimHei → 文泉驿 → DejaVu Sans`
的顺序自动查找，Windows 上一般不会出问题；Linux 环境装一下
`fonts-wqy-zenhei` 即可。

**找不到模型权重 / 评估结果**
`models/` 下的权重和结果是运行产物，没有进版本库。
按 README 顺序跑一遍训练与评估即可生成，或直接运行
`python tools/verify_repro.py` 检查当前状态。

## 训练耗时参考

在无 GPU 的纯 CPU 环境下（约 8 核），16 类 4287 张训练图、224×224 输入：

| 阶段                         | 每 epoch  | 合计               | 可训练参数             |
| ---------------------------- | --------- | ------------------ | ---------------------- |
| 阶段一（冻结主干）           | 约 145 秒 | 12 epoch ≈ 29 分钟 | 0.02M / 2.24M（0.9%）  |
| 阶段二（解冻 features[14:]） | 约 170 秒 | 10 epoch ≈ 28 分钟 | 1.70M / 2.24M（75.8%） |

传统方法基线（特征抽取 + KNN/SVM）在 CPU 上约 3 分钟。

> 注：阶段二只解冻了最后 5 个 block，但 MobileNetV2 靠后的 block 通道数多、
> 参数量集中，所以可训练参数已占全网络的四分之三。
